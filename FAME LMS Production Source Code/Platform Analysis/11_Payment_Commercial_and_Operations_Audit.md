### 1.2 Public-Facing Package Display

**Real Packages Page**: `/Landing/Home/OurPackages`
- Model: `List<WebsitePackageVM>` — database-driven, dynamically rendered
- Features: Plan name, subtitle, description, feature list with icons
- Flexible column layout with `LeftColumnWidth`/`RightColumnWidth`
- **Assessment**: ✅ Well-structured, data-driven, maintainable

**Broken Packages Page**: `/Home/Pricing`
- Shows **USD pricing** ($9/mo, $19/mo, $29/mo) — completely irrelevant to PKR audience
- Links to `learnly-signup.html` — **non-existent pages** (404 errors)
- Uses old template design (Learnly theme)
- **Assessment**: ❌ Must be removed or redirected — actively damaging

**Old Packages Page**: `/Home/Packages`
- Model: `PackageVM` — lists packages with basic info
- Static pagination (hardcoded Prev/1/2/Next without logic)
- Links to `/Home/Package_Preview/{id}` for details
- **Assessment**: ⚠️ Functional but outdated design

### 1.3 Pricing Presentation Issues

| Issue | Impact | Severity |

### 2.2 JazzCash Integration Review

**File**: `Views/Enrollment/JazzCash.cshtml`

| Aspect | Observation | Concern |
|--------|-------------|---------|
| **Layout** | Uses `_Layout.cshtml` (old layout) | Visual discontinuity from student portal |
| **Merchant ID** | Hardcoded: `"Merc0003"` | Possible sandbox/test merchant |
| **Password** | Hardcoded: `"0123456789"` | Clearly a test password |
| **Amount** | Hardcoded to `5600` | Not dynamic based on package selection |
| **Secure Hash** | Exposed in client-side JavaScript | Security concern |
| **3DS Integration** | Uses `PayChk3DS.js` | ✅ 3D Secure is a PCI requirement |
| **Response Display** | Shows JazzCash response via session variables | Basic but functional |

**Assessment**: The JazzCash integration appears to be a **development/sandbox implementation** that has not been productionized. The hardcoded values, test credentials, and fixed amount suggest it may not be the active payment pathway. Students likely pay via **manual bank transfer** with admin verification.

### 2.3 Payment Flow Gaps

| **No payment confirmation page** | After payment, no clear "payment received" acknowledgment | High |

| **No automated enrollment** | Admin must manually activate subscriptions after payment | High |

## 3. Manual Operational Dependencies

### 3.1 Operations Requiring Admin Intervention

| Operation | Manual Step | Impact |
|-----------|-----------|--------|
| **New Student Registration** | Admin reviews and approves registration request | Access delay — unknown SLA |
| **Subscription Activation** | Admin adds enrollment via `Enrollment/Index.cshtml` | Bottleneck if admin is unavailable |
| **Device Deletion** | Admin approves device delete request | Student locked out until approval |
| **Password Reset** (admin-side) | Admin can reset via student management | Supplements self-service forgot password |
| **Email Verification** (admin-side) | Admin can verify email manually | Bypass verification for edge cases |
| **Installment Tracking** | Admin manages via `Request/InstallmentList.cshtml` | Manual financial reconciliation |
| **Certificate Issuance** | Rules-based but admin can issue manually | Some certificates require manual trigger |
| **Support Tickets** | Admin/Agent responds to tickets | Standard but no SLA framework visible |
| **Coupon Management** | Admin creates coupons (feature currently disabled) | Promotional capability exists but dormant |

### 3.2 Operational Bottleneck Assessment

**Finding**: The platform has a **high degree of admin dependency** for core business operations, particularly:

1. **Registration → Access path** — Entirely admin-gated
2. **Payment → Enrollment** — Manual activation required
3. **Device management** — Admin approval for resets

This creates single-point-of-failure risk if the admin (likely Dr. Atif or a small team) is unavailable. It also limits scaling — each new student requires manual intervention.

## 4. Refund Clarity Review

| Aspect | Status | Evidence |
|--------|--------|---------|
| **Refund policy page** | ❌ Not found | Not in Terms & Conditions or as a separate page |
| **Refund mention in T&C** | ❌ Not found | Terms cover disclaimers and IP but not refunds |
| **Refund communication** | ❌ Not visible | No FAQ answer about refunds, no policy link |
| **Chargeback procedures** | ❌ Not documented | No guidance on dispute resolution |

**Impact**: Absence of a refund policy creates:
1. **Legal risk** — Consumer protection regulations in Pakistan and other jurisdictions may require clear refund terms
2. **Trust risk** — Prospective students may hesitate to pay without knowing refund options
3. **Operational risk** — Refund requests handled ad-hoc without standard process
